# Руководство администратора СмартСклад

## Назначение

Документ описывает установку, резервное копирование, восстановление, отчёт по email, импорт из 1С и права доступа. Все значения и названия кнопок сверены с текущим кодом.

## Установка на новом ПК

### Что нужно установить

- PostgreSQL 15 или новее;
- Python 3.11 или новее;
- утилиты PostgreSQL `pg_dump` и `pg_restore`.

**Важно:** `pg_dump` и `pg_restore` должны быть доступны в `PATH` или корректно заданы через путь к `pg_dump` на странице `/backups`. Без `pg_dump` приложение может работать, но копии не создаются. Без `pg_restore` копии создаются, но восстановление невозможно.

### 1. Создайте роль и базу PostgreSQL

Откройте PowerShell от имени пользователя, который может управлять PostgreSQL, и выполните:

```powershell
psql -U postgres -c "CREATE ROLE smartsklad LOGIN PASSWORD 'smartsklad';"
psql -U postgres -c "CREATE DATABASE smartsklad OWNER smartsklad;"
```

Команда создания базы нужна только при первой установке. Если роль или база уже существуют, создайте их с теми же именем, владельцем и паролем либо используйте существующие значения в `DATABASE_URL`.

### 2. Подготовьте Python и зависимости

Из корня проекта выполните:

```powershell
py -3.11 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
```

Команда запускается из каталога, где находится `requirements.txt`, `.env.example` и `alembic.ini`.

### 3. Заполните `.env`

Откройте `.env` и задайте подключение к базе:

```dotenv
DATABASE_URL=postgresql+psycopg://smartsklad:smartsklad@localhost:5432/smartsklad
ADMIN_USERNAME=admin
ADMIN_PASSWORD=changeme123
```

Для первого входа смените `ADMIN_PASSWORD` на безопасный пароль. Если пароль базы содержит специальные символы, URL-кодируйте их в `DATABASE_URL`.

Параметры SMTP заполняются отдельно, когда нужен email:

```dotenv
SMTP_HOST=
SMTP_PORT=587
SMTP_USER=
SMTP_PASSWORD=
SMTP_FROM=
```

Пустой `SMTP_HOST` означает, что отчёт записывается как ошибка «SMTP не настроен». При отправке документа заказа страница сообщает о нём, а подробность зависит от выбранного канала. Подробности приведены ниже.

### 4. Примените миграции

При активном виртуальном окружении выполните:

```powershell
alembic upgrade head
```

Без активации окружения используйте эквивалентную команду:

```powershell
.\.venv\Scripts\python.exe -m alembic upgrade head
```

### Обновление существующей установки

После обновления до версии с импортом из 1С выполните `alembic upgrade head` ещё раз: новая ревизия `5d8c1e4a7b90` создаёт таблицу `import_map`, в которой хранится соответствие записей выгрузки 1С уже созданным строкам базы. Без неё `/import` вернёт ошибку. Миграция только добавляет таблицу, существующие данные не меняет.

После обновления до версии со справочником единиц `alembic upgrade head` нужен ещё раз, теперь с ревизией `8e2f1a9c4b71` (родитель — `5d8c1e4a7b90`). Миграция:

- создаёт таблицу `units` (`name varchar(32)`, `is_deleted`, `created_at`, `updated_at`) и заполняет её 34 названиями по умолчанию;
- добавляет в `products` колонку `unit_id`, переносит в неё значения прежней строковой колонки `unit`, **придумывая недостающие единицы**: название, которого в справочнике ещё нет, создаётся автоматически, чтобы не потерять ни один товар;
- делает `unit_id` `NOT NULL`, добавляет внешний ключ на `units.id` и удаляет колонку `unit`.

Прежняя колонка `products.unit` была `varchar(32) NOT NULL` со значением по умолчанию `шт`, поэтому пустой единицы у товара в базе быть не могло и перенос покрывает все строки. Откат есть: `downgrade` возвращает строковую колонку и наполняет её названиями единиц, после чего дропает `unit_id` и саму `units`.

### 5. Запустите приложение

```powershell
uvicorn "app.main:app"
```

Для запуска тем же интерпретатором, которым установлены зависимости:

```powershell
.\.venv\Scripts\python.exe -m uvicorn "app.main:app"
```

При первом запуске на пустой базе lifespan создаёт администратора из `ADMIN_USERNAME` и `ADMIN_PASSWORD`. Откройте `/login` и войдите.

## Проверка утилит PostgreSQL

### Windows PowerShell

```powershell
where.exe pg_dump
where.exe pg_restore
pg_dump --version
pg_restore --version
```

В `cmd.exe` те же команды пишутся как `where pg_dump` и `where pg_restore`.

### Linux

```bash
which pg_dump
which pg_restore
pg_dump --version
pg_restore --version
```

Если команды не находятся, добавьте каталог с утилитами PostgreSQL в `PATH` и перезапустите приложение. Проверка окружения на `/backups` показывает найденный путь, версии утилиты и сервера, а также доступность папки для записи.

Если утилиты установлены вне `PATH`, укажите в поле «Путь к pg_dump» полный путь к файлу `pg_dump.exe`. В этом случае `pg_restore` должен находиться рядом с ним под именем `pg_restore.exe`; панель и восстановление используют этот соседний файл. Если указан неверный путь, панель покажет, что утилита не найдена.

## Резервные копии

Откройте `/backups`. Раздел доступен пользователю с правом `backup.manage`; по умолчанию это администратор. Панель содержит состояние планировщика, проверку окружения, настройки копирования, настройки отчёта, список архивов и последние запуски.

### Значения по умолчанию

При первом обращении к базе создаётся одна строка настроек:

| Настройка | Значение |
|---|---|
| Автоматическое копирование | включено |
| Время запуска | `03:00` |
| Период проверки | `15` минут |
| Срок хранения | `30` дней |
| Папка для копий | `backups/` в корне проекта |
| Путь к `pg_dump` | пусто, искать в `PATH` |

Период проверки можно задать от 1 до 1440 минут. Срок хранения — от 1 до 365 дней. Время запуска вводится в формате `ЧЧ:ММ`. Папка должна быть доступна для записи.

### Ручная копия

Нажмите «Создать копию сейчас». Копия создаётся даже при выключенном автоматическом запуске. После успешного завершения файл появится в списке «Резервные копии», а запись — в «Последние запуски».

Дамп выполняется утилитой в формате custom и сначала записывается во временный файл `.part`. Только после успешного завершения временный файл переименовывается в `.dump`. Прерванный дамп не должен выглядеть как рабочая копия.

После каждой успешной копии удаляются архивы, дата которых строго старше срока хранения. Удаление выполняется по дате в имени файла, а не по дате изменения файла.

### Проверка окружения

Блок «Состояние планировщика» показывает состояние проверки, время следующей копии и следующего отчёта, а также индикатор работы планировщика. Во время обратного отсчёта и восстановления плановые копирование и отчёт пропускаются. Блок «Проверка окружения» показывает:

- найденный `pg_dump`;
- найденный `pg_restore`;
- версию утилиты;
- версию сервера;
- доступность папки для записи.

Красное сообщение `pg_dump не найден` означает, что автоматические и ручные копии завершатся ошибкой. Красное сообщение о версии означает, что `pg_dump` старее сервера и PostgreSQL откажется снимать дамп. Установите утилиту той же или более новой версии.

Отсутствие `pg_restore` не мешает созданию копий, но делает восстановление невозможным, пока утилита не будет найдена.

## Восстановление

**Восстановление можно потерять данные. Проводите его только на тестовой копии базы, пока не убедитесь, что архив и процедура проверены.**

### Порядок действий

1. Откройте `/backups` и скачайте нужный архив или заранее сохраните его в безопасном месте.
2. Убедитесь, что выбрана правильная копия и что её файл находится в папке архивов.
3. Нажмите «Восстановить» у нужного файла.
4. В форме используется задержка 60 секунд. В самом сервисе допустимый диапазон — от 10 до 3600 секунд.
5. Во время обратного отсчёта не редактируйте заказы, клиентов, товары и настройки: эти изменения могут быть потеряны. В баннере показано абсолютное время начала; кнопка «Отменить восстановление» сбрасывает отсчёт.
6. После начала восстановления страницы и API, кроме разрешённых служебных маршрутов, отвечают HTTP 503. Для обычных страниц показывается страница технического обслуживания, для API — JSON с описанием восстановления.
7. После завершения приложение возвращается в работу автоматически. Во время `pg_restore` отменять восстановление нельзя.

Восстановление выполняет `pg_restore --clean --if-exists --no-password` в существующую базу. База не пересоздаётся ключом `--create`. Пароль передаётся утилите через переменную `PGPASSWORD`, а не через аргументы командной строки.

### Что откатывается

Восстановление возвращает состояние всей базы из архива, включая:

- таблицу сессий `sessions`: сессии, созданные до снятия копии, остаются действительными, а созданные после копии исчезают;
- таблицу общих настроек `settings`;
- таблицу настроек резервного копирования `backup_settings`;
- журнал аудита `audit_log`;
- заказы, клиентов, товары и остальные данные.

Несохранённые изменения, сделанные после снятия копии, исчезнут. Сам факт восстановления затем добавляется в журнал запусков и аудит уже в восстановленную базу.

### Один процесс приложения

Состояние режима обслуживания хранится в памяти процесса. Запускайте приложение одним процессом, особенно при использовании восстановления. Не используйте несколько workers для этого сценария: фоновые задачи защищаются advisory-lock, но состояние режима обслуживания между процессами не разделяется.

## Отчёт по email

### Настройка SMTP

В `.env` укажите:

```dotenv
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_USER=report@example.com
SMTP_PASSWORD=secret
SMTP_FROM=report@example.com
```

Порт по умолчанию — `587`. Приложение использует `SMTP` и `STARTTLS`; если SMTP-сервер не поддерживает TLS на указанном порту, отправка завершится ошибкой. После изменения `.env` перезапустите приложение.

### Настройка расписания

В `/backups` откройте блок «Отчёт по email»:

- включите «Отправлять отчёт по расписанию»;
- выберите, как часто отправлять отчёт: каждый день, раз в неделю или раз в месяц; это одновременно период данных в отчёте;
- укажите время отправки;
- выберите получателей;
- нажмите «Сохранить».

Значения по умолчанию: отчёт выключен, период `week`, время `09:00`, получателей нет. Для `day` отчёт ожидает следующего календарного дня, для `week` — семи дней с последнего планового запуска, для `month` — 30 дней. Плановый запуск сохраняет `last_report_scheduled_at`; ручная отправка его не меняет и не отменяет следующий плановый запуск.

Кнопка «Отправить отчёт сейчас» выполняет одну отправку по сохранённым настройкам. Расписание и список получателей не изменяются; ручная отправка обновляет только `last_report_at`, `last_report_sent` и `last_report_skipped`. Количество ошибок (`failed`) показывается только в экранном сообщении и не сохраняется; причины по каждому получателю находятся в `notification_log`.

Отчёт содержит период, количество заказов, сумму продаж, средний чек и CSV-вложение с продажами по дням. Каждому выбранному пользователю отправляется отдельное письмо.

### Почему пользователя без email нет в списке

В списке получателей отображаются только активные пользователи с непустым корректным email. При сохранении несуществующий или неактивный id, пустой адрес и некорректный адрес отклоняются с сообщением об ошибке. Пользователь без email принципиально не может получить письмо, поэтому его нельзя выбрать в панели.

Если ранее сохранённый id пользователя остался в настройках, а email позднее удалили, отчёт пропустит его и увеличит счётчик «пропущено». Панель показывает только этот счётчик, а не имя пропущенного пользователя. Имя пользователя находится в журнале уведомлений: там будет запись `email` со статусом `failed`, recipient с username и причиной «у пользователя не указан email».

## Импорт данных из 1С

### Право и папка выгрузки

Раздел `/import` и API `/api/import/*` доступны по праву `import.manage`. В системных ролях его нет: изначально им владеют только администратор (суперроль) и суперпользователи. Продавец, кладовщик и менеджер не видят ссылку «Импорт» в меню, а прямой запрос `/import` получает HTTP 403. Выдать право можно вручную через `/roles`.

Папка с выгрузкой задаётся общей настройкой `import_path` и редактируется на странице `/import` в поле «Путь» с кнопкой «Сохранить» либо через `PUT /api/import/path`. Значение по умолчанию — `.system_folder/1c_export`. Относительный путь отсчитывается от корня проекта, абсолютный используется как есть; пустое значение отклоняется. Настройка попадает в журнал аудита как `settings.update`.

Читаются только файлы `*.json` непосредственно из папки, без подпапок. Указывается имя файла без пути, а ссылка (в том числе symlink) за пределы папки отклоняется.

### Формат выгрузки

Один объект JSON с любым подмножеством разделов `products`, `customers`, `orders`; отсутствующие разделы считаются пустыми. Файл читается как UTF-8 с BOM, переносы строк не обязательны — файл может быть одной строкой. Несколько файлов сливаются: можно положить один общий файл или три файла по разделам и отметить их все. Разделы, отличные от трёх известных, игнорируются; не список объектов в известном разделе — ошибка. Заблокированный файл (открыт в Excel) даёт понятную ошибку, а не падение.

### Правила сопоставления

- Сначала запись выгрузки ищется в таблице `import_map` по её `id` из 1С, затем — по названию без учёта регистра и лишних пробелов среди неудалённых строк. Помеченные удалёнными строки считаются отсутствующими, для них создаются новые. Совпадений нет — создаётся новая строка. Повторяющийся `id` внутри одной выгрузки (обычная копия документа в 1С) пропускается и попадает в `skipped`, а не обрывает импорт.
- `import_map` (`entity_type`/`source_id`/`entity_id`/`source_label`, уникальность на первых двух колонках) заполняется только при создании: строки появляются для созданных товаров, клиентов, служебного клиента и для каждого импортированного заказа. Товар или клиент, найденный по названию, строки в таблице не получает, и повторный прогон защищает его от дубля сопоставлением по названию, а не таблицей. Номер заказа из 1С хранится в `source_label`, у товаров и клиентов это поле пустое: название и так лежит в самой строке, а в 1С оно бывает длиннее, чем ширина колонки `varchar(64)`.
- Артикул в выгрузке отсутствует, а `products.sku` — `NOT NULL` с уникальностью, поэтому он синтезируется как `1C-00001`, `1C-00002`… с пропуском уже занятых значений.
- ИНН принимается при 10 или 12 цифрах либо пустым. Значение другой длины отбрасывается, ИНН остаётся пустым, а количество таких записей попадает в отчёт как `inn_dropped`. Ручной ввод ИНН в карточке клиента использует то же правило.
- Заказы импортируются только в статусе `done` с датой из выгрузки: они уже проданы. Номер заказа берётся из собственной нумерации приложения. Остатки не импортируются и не меняются — в выгрузке их нет, а повторное списание привело бы к отрицательным остаткам.
- Дата из выгрузки — местное время сервера 1С, и она сохраняется в часовом поясе хоста, на котором запущено приложение. Отчёт по продажам, письмо со сводкой и прогноз спроса группируют заказы по дням в часовом поясе сессии PostgreSQL, поэтому **часовой пояс хоста должен совпадать с часовым поясом сервера 1С**. Если это не так, заказы, попавшие в 1С между 21:00 и 24:00, уедут в отчётах на следующий день.
- Скидка импортированного заказа берётся из `Customer.personal_discount` (`discounts.get(customer_id, 0.0)`), а `recalc_total` умножает сумму позиций на `(1 − discount/100)`. У клиентов, созданных импортом, скидка нулевая, поэтому их заказы сходятся с выгрузкой; у клиента, найденного по имени и имеющего персональную скидку, итог легитимно меньше суммы позиций. Расхождение с файлом для таких заказов — ожидаемое поведение, а не ошибка импорта.
- Позиции заказа: если строка ссылается на известный товар, название и единица берутся из его карточки, цена — из выгрузки. Если ссылка указывает на товар, которого нет ни в базе, ни в плане текущего прогона, но название есть, `_item_product` создаёт новый товар по этому названию с нулевыми ценой и остатком и привязывает строку к нему. Такой товар учитывается отдельно в `orders.products_from_items` и не входит в `products.created`; это единственный счётчик, соответствующий числу реально созданных товаров из позиций — он считает только те заказы, которые действительно импортируются, и пропущенный заказ в него ничего не добавляет. Одно и то же неизвестное название в разных заказах даёт отдельную карточку в каждом заказе со своим артикулом — автоматической склейки по названию здесь нет. Повторы одного товара в заказе склеиваются с количеством и средневзвешенной ценой, так что сумма позиции равна сумме исходных строк файла. Заказ без строк считается `empty_orders` и попадает в предупреждения.
- Заказ без контрагента относится к служебному клиенту `Без контрагента (1С)`, который создаётся один раз.

### Что не переносится из выгрузки

Импорт читает только `id`, `name`, `unit`, `inn`, `date`, `customer_id` и `items` (в позиции — `product_id`, `name`, `unit`, `quantity`, `price`). Остальные поля выгрузки игнорируются без предупреждения. Следствия:

- товар создаётся с `price=0.0`, `rest=0`, `track_rest=True`, без категории и характеристик, даже если в выгрузке цена, категория и характеристики были;
- клиент создаётся только с именем, ИНН и нулевой персональной скидкой — телефон, email и номер скидочной карты остаются пустыми;
- у клиентов, найденных по имени, эти поля не меняются: импорт их не трогает.

Из-за пустого email у импортированных клиентов отправка заказа кнопкой «На email» недоступна: канал возвращает ошибку «у клиента не указан email» (`notifications/service.py`). Для выгрузки на 5 854 товара это означает 5 854 товара с нулевой ценой, которые нужно заполнить вручную, и 995 клиентов без контактов.

### Транзакция и аудит

Импорт выполняется в одной транзакции: любая ошибка откатывает всё, включая созданных до неё товаров и клиентов. Кнопка «Разобрать» (предпросмотр) ничего не пишет, а разбор с импортом считаются одним и тем же кодом (`plan_import` и `run_import` делят `_build`/`_report`), поэтому числа совпадают. Единственное исключение — товары из строк заказов: они попадают в `orders.products_from_items`, но не в `products.created`, и отдельной строки для них на странице `/import` нет. Если в выгрузке есть позиции с неизвестным товаром, фактическое число новых товаров окажется больше показанного; в проверенной выгрузке `Export27` таких позиций нет, поэтому там счётчик совпадает.

Запись аудита добавляется в ту же транзакцию, а фиксирует её единственный `db.commit()` в конце `run_import`, поэтому сбой в любой момент, включая сбой сразу после записи аудита, откатывает импорт целиком.

Каждый прогон записывается в журнал аудита как действие `import.run` с типом сущности `import` и полным отчётом в `new_value`. Учтите: **текст предупреждений виден только в разборе**. После импорта страница сообщает лишь их количество, а повторный разбор того же файла возвращает ноль предупреждений, потому что уже сопоставленные заказы отбрасываются до проверки позиций. Единственная постоянная копия — поле `new_value` в записи `import.run`, и там лежит **весь** список предупреждений: полный — в `orders.warnings`, а ключ `warnings` в том же JSON обрезан до первых 50 для показа на странице.

### Остатки после импорта

У импортированных товаров остаток 0, а «Учитывать остатки» включается принудительно: настройка `stock_track_default` на импорт не действует и работает только при создании товара вручную (`inventory/service.py:160`). Поэтому новые заказы на импортированные товары отклоняются до ручного ввода остатков.

Массовых действий нет: в списке товаров доступна только смена категории, а остаток и «Учитывать остатки» правятся в карточке товара по одному, пользователем с правом `stock.change`. Для выгрузки на 5 854 товара это либо 5 854 отдельные правки, либо решение работать без учёта остатков. Остатки из отдельной выгрузки сейчас не импортируются.

## Единицы измерения

### Право `units.manage`

Справочник `/units` и изменение единиц в API `/api/units` (POST, PATCH, DELETE) требуют права `units.manage`; в системных ролях его нет, поэтому в свежей установке раздел видит только администратор (суперроль) и суперпользователи. Продавец, кладовщик и менеджер не видят ссылку «Единицы измерения» в меню, а прямой запрос `/units` получает HTTP 403. Выдать право — через `/roles`, метка в списке прав «Единицы измерения».

Отдельно: **чтение** справочника открыто всем, у кого есть `products.view` — `GET /api/units` отдаёт `[{id, name}]` без удалённых записей, по возрастанию названия. Этого достаточно, чтобы форма товара показала список единиц, поэтому `products.view` и не нужно расширять.

Ошибки сервиса отдаются как HTTP 422 с русским текстом: «название единицы обязательно», «название длиннее 32 символов», «единица с таким названием уже есть», «единица не найдена», «единица используется товарами». На странице те же сообщения приходят в `?msg=` после 303.

### Набор по умолчанию и почему он неполный

Справочник стартует с 34 названий — это `DEFAULT_UNITS` из `inventory/service.py` (в миграции `8e2f1a9c4b71` продублировано тем же списком). Названия приведены как есть, в порядке сида:

```python
DEFAULT_UNITS = (
    "шт", "кг", "г", "т", "л", "мл", "м", "м2", "м3", "см", "мм",
    "упак", "ящ", "короб", "пач", "пакет", "бут", "бан", "вед", "пал",
    "пара", "компл", "набор", "рул", "ед", "ч", "мин", "сут", "дюжина",
    "лист", "кат", "дюйм", "фут", "галл",
)
```

Ищите единицу в `/units` именно по этой строке: «шт», а не «штука», «м2», а не «м²».

**Это отправная точка, а не закрытый список, и это осознанное решение.** Набор покрывает типовую оптовую и розничную торговлю, но справочник ничего не знает про сокращения и синонимы конкретного предприятия, поэтому в выгрузке 1С могут встретиться строки, которых в нём нет (например, «ГРАММ» рядом с «г» или «шт» рядом с «штука»). Автоматически добавлять их при импорте нельзя: в справочнике оседали бы дубли, и товары со временем разъезжались бы по единицам. Поэтому неизвестные единицы импорт не создаёт молча, а останавливается и предлагает владельцу решить, что с ними делать (см. «Разрешение единиц при импорте»).

`ensure_default_units` вызывается в lifespan при каждом старте и **только дописывает** недостающие названия. Набор уже имеющихся строк собирается со **всех** строк таблицы, без фильтра `is_deleted`, и сравнение точное, без учёта регистра. Отсюда два следствия:

- удалённую вами единицу из набора по умолчанию он не вернёт — строка есть, пусть и с `is_deleted = true`;
- **переименование единицы из набора по умолчанию откатывается на следующем старте**: переименовали «г» в «грамм» — «г» в `DEFAULT_UNITS` больше не найдётся, и приложение допишет его заново отдельной строкой. В справочнике окажутся обе строки: старая с вашими товарами и новая пустая.

Это известное ограничение, а не рекомендация: добавление фильтра `is_deleted` вернуло бы удалённые единицы назад. Планируя переименование единицы из набора по умолчанию, учитывайте, что исходное название вернётся.

Счётчика созданных единиц в отчёте импорта нет — единственный список созданных единиц это сам справочник `/units`.

### Переименование меняет карточки, но не историю

Единица у товара хранится ссылкой (`products.unit_id`), а `Product.unit` — это свойство, читающее название связанной единицы. Поэтому переименование единицы сразу меняет её вид на всех карточках товаров, которые её используют, без правки самих товаров и без записи в аудит по каждому товару: в журнал попадает только `unit.update` с типом сущности `unit`, где `old_value` — прежнее название, `new_value` — новое.

Переименование **в то же самое название отклоняется** с «единица с таким названием уже есть»: проверка дублей ищет по всем неудалённым строкам и находит ту, которую переименовывают, — она не исключается из поиска по `id`, в отличие от категорий, где такое исключение есть. Форма не требует менять текст, так что отправка неизменённого названия — обычный сценарий, и он завершается ошибкой, а не тихим успехом.

В позициях заказов (`order_items.unit_snapshot`) лежит **строка** — название на момент продажи. Это намеренно: будь это ссылка, переименование единицы задним числом переписало бы историю уже закрытых заказов и испортило печатные формы и уведомления, отправленные клиенту. Побочный эффект тот же, что и у снимков цены: после переименования в старых заказах останется старое название, а в карточке товара — новое. Это расхождение ожидаемо, а не ошибка.

### Удаление

Удаление мягкое: строка помечается `is_deleted` и пропадает из списков и из выпадающих списков форм. Отказ «единица используется товарами» срабатывает, если на единицу ссылается **любой** товар — в запросе нет фильтра `is_deleted`, поэтому помеченный удалённым товар тоже мешает (`inventory/service.py:398`). Сначала переведите такие товары на другую единицу, потом удаляйте.

Восстановить удалённую единицу из интерфейса нельзя, но завести с тем же названием заново можно: проверка дублей смотрит только на неудалённые строки.

### Ломающее изменение в JSON API

Единица у товара переехала со строки на ссылку, поэтому в payload создания и обновления товара поле изменилось:

| | Было | Стало |
|---|---|---|
| `POST /api/products` | `"unit": "кг"` (строка, по умолчанию `"шт"`) | `"unit_id": 12` (целое, по умолчанию `null`) |
| `PATCH /api/products/{id}` | `"unit": "кг"` или `null` | `"unit_id": 12` или `null` |

Запрос со старым полем `unit` больше не работает: неизвестные поля сервер просто игнорирует, поэтому при создании товар получит единицу по умолчанию («шт»), а при обновлении единица не изменится вовсе. Внешних потребителей у JSON API нет, но если вы готовили выгрузку или свою интеграцию — правится она. Ответы при этом не похужели: `GET /api/products` и карточка товара отдают **оба** поля, `unit` — название строкой и `unit_id` — числом, так что читать название по-прежнему удобно.

Поведение нового поля — у создания и обновления **разное**, и это важно для частичных запросов:

| | `unit_id` не передан | `"unit_id": null` | несуществующий или удалённый `id` |
|---|---|---|---|
| `POST /api/products` | товар штучный, «шт» | товар штучный, «шт» | HTTP 409 «единица не найдена» |
| `PATCH /api/products/{id}` | **единица не трогается** | товар переводится на «шт» | HTTP 409 «единица не найдена», товар не меняется |

Причина в том, что `PATCH` получает только явно переданные поля (`model_dump(exclude_unset=True)`), а `update_product` меняет единицу лишь если ключ `unit_id` присутствует. Отсюда практическое правило: **частичный PATCH без `unit_id` не сбрасывает единицу на «шт»**, а `null` — сбрасывает. Если интеграция шлёт `null` вместо отсутствующего поля, товар молча станет штучным.

Значение не является целым — отвергается проверкой схемы (HTTP 422), до сервиса не доходит.

Право `unit_id` в PATCH проверяется как `products.edit` — это обычное поле карточки, отдельного права на смену единицы нет.

### Разрешение единиц при импорте

Экран решения единиц — часть `/import`; механика для пользователя описана в руководстве пользователя, здесь то, что важно администратору.

- `plan_import`/`run_import` собирают множество всех единиц из выгрузки — и из раздела `products`, и из позиций заказов — и ищут каждую в справочнике через `get_unit_by_name` (сравнение без учёта регистра и лишних пробелов, только среди неудалённых). Ненайденные возвращаются в `report.unresolved_units` как строки 1С.
- Пока список не пуст, `run_import` **отказывается** работать: `ValueError("не заданы единицы: …")`, и на странице форма импорта не рендерится. Это защита на сервере, а не только в шаблоне, — прямой `POST /import/run` без решений тоже ничего не запишет. Если среди неразрешённых строк есть длиннее 32 символов, к сообщению добавляется приписка про предел длины: такую единицу нельзя завести ни под каким решением, её надо сначала сократить в форме.
- Форма решения отдаёт значение в виде `unit_map[<строка 1С>]`: числовой `id` существующей единицы либо пустое `new:` — во втором случае название подставляет сервер из поля `unit_name[<строка 1С>]`, которое на странице уже заполнено строкой 1С и редактируется. Если это поле **очистить**, решение остаётся буквально `new:` с пустым именем, и `_build` падает с «название единицы обязательно». Ошибка приходит в `?msg` на `/import` после 303, форма решения там не отрисовывается — её нужно открыть заново кнопкой «Разобрать»; в базе не пишется ничего. Ошибка честная и безопасная, но выглядит неочевидно, поэтому пустое поле лучше не оставлять. Всё это разбирает `_parse_unit_map` в `app/main.py`.
- Вариант `new:<название>` **переиспользует уже существующую единицу**, если название совпало (сравнение без учёта регистра и лишних пробелов, только среди неудалённых): новая строка не создаётся, предупреждения нет, записи `unit.create` в аудите не будет. Это единственный случай, где «завести новую» и «подставить существующую» сходятся, и он безопасен — дубля в справочнике не появится, — но знать о нём стоит: если вы рассчитывали, что появится единица под новым названием, её не будет, будет использована существующая.
- `unit_map` **нигде не хранится**: ни в таблице, ни в сессии, ни в настройках. Он живёт только в теле текущего POST — форма `/import/run` повторно тащит те же значения скрытыми полями, а повторное нажатие «Разобрать» в блоке файлов отбрасывает решения и предлагает единицы заново. Следствие: решение всегда нужно принять заново, сохранить его «на потом» нельзя.
- Единицы, созданные решением, заводятся с `commit=False` внутри `_build`, то есть в той же транзакции, что и товары, клиенты и заказы: если импорт упал, откатываются и они. Разбор (`plan_import`) создаёт их так же, но коммита в нём нет, а сессия закрывается откатом, поэтому предпросмотр не добавляет единиц. Отдельного счётчика созданных единиц в отчёте нет — смотрите справочник.
- Числовой `id`, которого нет или который указывает на удалённую единицу, даёт `ValueError("единица не найдена: …")`. Прогон прерывается, и в базе не остаётся ничего: даже единицы, заведённые ранее в этом же проходе, откатываются вместе с транзакцией.
- В отчёте есть `unit_map` с названием справочной единицы для каждой строки 1С, а на странице этот список показывается блоком «Применённые единицы измерения» только когда решения действительно были поданы. Его и стоит вычитывать перед импортом.

## Роли и права

Права проверяются по роли пользователя. Администратор — суперроль и имеет все права независимо от списка. Системные роли создаются с такими правами:

| Роль | Права по умолчанию |
|---|---|
| Администратор | все права |
| Продавец | просмотр товаров, клиенты, просмотр/создание/редактирование/смена статуса заказов |
| Кладовщик | просмотр товаров, изменение остатков, просмотр заказов, смена статусов |
| Менеджер | просмотр товаров, изменение цен, клиенты, все операции с заказами, аналитика, экспорт отчётов, отправка и просмотр уведомлений |

Дополнительно существуют права:

- `backup.manage` — `/backups`, ручная копия, настройки, скачивание, восстановление и ручная отправка отчёта;
- `import.manage` — `/import` и `/api/import/*`: список файлов, разбор, импорт, смена папки выгрузки;
- `units.manage` — `/units` и изменение единиц в `/api/units` (POST, PATCH, DELETE); чтение `GET /api/units` открыто по `products.view`;
- `settings.change` — общие настройки;
- `users.manage` — пользователи и роли;
- `audit.view` — журнал аудита;
- `reports.export` — экспорт CSV;
- `notifications.send` — отправка документов;
- `notifications.view` — журнал уведомлений.

Пользователь без `backup.manage` не видит ссылку «Резервные копии», а прямой запрос `/backups` получает HTTP 403.

## Решение проблем

### Бэкапы не снимаются

1. Откройте `/backups` и проверьте «Проверка окружения».
2. Проверьте `pg_dump --version` и путь к папке.
3. Убедитесь, что папка существует и доступна для записи.
4. Если `pg_dump` установлен вне `PATH`, укажите полный путь к `pg_dump.exe` в настройках.
5. Нажмите «Создать копию сейчас» и проверьте «Последние запуски».

### Версия `pg_dump` старее сервера

Установите `pg_dump` версии сервера PostgreSQL или новее. Панель заранее показывает major-версии утилиты и сервера. Пока версия утилиты меньше, создание дампа будет отклонено PostgreSQL.

### SMTP не настроен

Проверьте `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD` и `SMTP_FROM` в `.env`, перезапустите приложение и нажмите «Отправить отчёт сейчас». При пустом `SMTP_HOST` результат будет содержать ошибки, а в журнале появится запись с текстом «SMTP не настроен».

### После восстановления изменились сессии

Таблица `sessions` возвращается к состоянию на момент снятия копии. Сессия, созданная до копии, остаётся действительной; сессия, созданная после копии, исчезает, и её пользователю потребуется войти снова. Настройки и журнал аудита также возвращены к состоянию архива.

### Импорт не находит файлы

Проверьте, что файлы лежат непосредственно в папке из поля «Путь» на `/import`, имеют расширение `.json` и что путь сохранён кнопкой «Сохранить». Перезапускать приложение после смены пути не нужно. Сообщение «файл за пределами папки импорта» означает, что имя файла содержит путь или что файл является ссылкой наружу.

### Файл выгрузки не читается

Обычная причина — файл открыт в Excel: закройте его и повторите. Сообщение «ожидался объект с разделами» означает, что в корне JSON лежит массив или другое значение вместо объекта с разделами `products`, `customers`, `orders`.

### После импорта не создаются заказы на товары

У импортированных товаров остаток 0 при включённом учёте остатков, потому что в выгрузке 1С остатков нет. Введите остатки в карточках товаров — по одному, массового действия в списке товаров нет, а глобальная настройка учёта остатков импортированные товары не меняет. Либо оставьте товары без учёта остатков, сняв галочку «Учитывать остатки» в каждой карточке.

### Панель показывает, что `pg_restore` не найден

Установите утилиту и добавьте её каталог в `PATH`. Если используется ручной путь к `pg_dump`, разместите `pg_restore` рядом с ним под тем же расширением. Затем обновите `/backups` и проверьте, что обе строки показывают найденные пути.
