# Чек-лист ручной проверки

Пункты 1–8 проверяют резервное копирование, восстановление и отчёт по email. Раздел 9 проверяет импорт из 1С.

## Общие условия

Проверки выполняются на отдельной тестовой базе или на копии рабочей базы. Не выполняйте восстановление на единственной рабочей копии.

Перед началом:

- запустите приложение из корня проекта;
- войдите под пользователем с правом `backup.manage`;
- откройте `/backups`;
- убедитесь, что в «Проверке окружения» найдены `pg_dump` и `pg_restore`, а папка доступна для записи;
- сохраните идентификатор тестовой базы и не используйте рабочие SMTP-данные без необходимости.

## 1. Ручная копия

1. Нажмите «Создать копию сейчас».
2. Дождитесь сообщения «Копия создана».
3. Обновите `/backups`.
4. Проверьте, что новый файл появился в таблице «Резервные копии».
5. В «Последних запусках» проверьте запись вида `manual` со статусом `success` и именем файла.

Ожидаемый результат: файл имеет имя вида `smartsklad-YYYYMMDD-HHMMSS.dump`, временного `.part` в списке нет.

## 2. Срок хранения

1. В настройках установите срок хранения `1` день и сохраните.
2. В тестовой папке создайте файл с корректным именем, например `smartsklad-20260101-000000.dump`. Это подготовка тестового архива: в интерфейсе отдельного поля для ручного имени нет.
3. Нажмите «Создать копию сейчас».
4. Проверьте список архивов.

Ожидаемый результат: после успешной копии старый файл исчез, а свежая копия осталась. Проверка выполняется только после успешного создания новой копии.

## 3. Отсутствие `pg_dump`

1. В настройках укажите заведомо неверный полный путь к `pg_dump` и сохраните.
2. Обновите `/backups` и проверьте блок «Проверка окружения».
3. Дождитесь планового запуска на тестовой базе. Для проверки можно установить время запуска в прошлом, включить автоматическое копирование и убедиться, что копии за текущий день ещё не было.
4. Проверьте «Последние запуски».
5. Откройте обычную страницу приложения, например `/products`.

Ожидаемый результат: в панели есть красное предупреждение о ненайденном `pg_dump`; в последних запусках есть ошибка планового запуска; приложение продолжает открываться и не падает.

После проверки верните корректный путь или очистите поле, чтобы копирование снова работало.

## 4. Восстановление на тестовой копии

**Обязательно выполнять только на тестовой копии базы.**

1. Создайте клиента и товар, если они ещё не нужны для сценария.
2. Создайте первый заказ и сохраните его номер.
3. Нажмите «Создать копию сейчас» и дождитесь успешного файла.
4. Создайте второй заказ с другим понятным номером или признаком.
5. Убедитесь, что второй заказ виден в `/orders`.
6. На странице `/backups` нажмите «Восстановить» у копии из шага 3. Форма использует задержку 60 секунд; во время обратного отсчёта не редактируйте данные. В баннере проверьте абсолютное время начала и при необходимости нажмите «Отменить восстановление».
7. После начала восстановления откройте обычную страницу приложения, например `/orders`. Кнопка отмены во время работы `pg_restore` не должна останавливать процесс.

Ожидаемый результат:

- во время работы `pg_restore` обычная страница отвечает HTTP 503;
- после завершения приложение снова открывается;
- второй заказ исчез;
- первый заказ остался;
- состояние сессий соответствует снятой копии: сессии, созданные до копии, остаются, а созданные после копии исчезают;

Если первый заказ тоже отсутствует либо появились неожиданные данные, остановитесь и не повторяйте восстановление на рабочей базе.

## 5. Advisory-lock и два процесса

Этот сценарий проверяется вручную на PostgreSQL, потому что тесты используют SQLite.

1. Подготовьте тестовую базу и одинаковый `.env` для двух процессов.
2. В `/backups` включите автоматическое копирование, установите период проверки `1` минуту и время запуска в прошлом. Убедитесь, что за текущий день автоматическая копия ещё не создавалась.
3. Запустите два отдельных процесса приложения из двух окон PowerShell одинаковой командой:

```powershell
uvicorn "app.main:app" --port 8001
```

и:

```powershell
uvicorn "app.main:app" --port 8002
```

Не используйте эти два процесса для рабочего режима восстановления: состояние технического обслуживания хранится в памяти процесса.

4. Дождитесь плановой проверки.
5. Сравните количество новых архивов и записей `scheduled` в «Последних запусках».

Ожидаемый результат: за один плановый момент создана одна копия, а не по одной копии на каждый процесс. Второй процесс должен получить advisory-lock и пропустить выполнение задания.

## 6. Отчёт по email

### Успешная ручная отправка

1. Настройте тестовый SMTP в `.env`, перезапустите приложение и создайте активного пользователя с корректным email.
2. В `/backups` откройте «Отчёт по email».
3. Выберите пользователя, настройте частоту и период данных, время, нажмите «Сохранить».
4. Нажмите «Отправить отчёт сейчас».

Ожидаемый результат: приходит одно письмо с отчётом и CSV-вложением. В панели появляется сообщение с количеством отправленных, пропущенных и ошибочных попыток. Расписание и список получателей не меняются; ручной запуск обновляет `last_report_at`, `last_report_sent` и `last_report_skipped`, а следующий плановый запуск всё ещё определяется по `last_report_scheduled_at`. Количество ошибок видно в сообщении, но не сохраняется; причины по получателям находятся в `notification_log`.

### Пропуск пользователя без email

1. Создайте пользователя с email, сохраните его в получателях и нажмите «Сохранить».
2. Удалите email у этого пользователя через карточку пользователя.
3. Не нажимайте «Сохранить» в настройках отчёта, чтобы сохранённый id остался в настройках.
4. Нажмите «Отправить отчёт сейчас».
5. Проверьте `/notifications` и счётчик «пропущено» в `/backups`.

Ожидаемый результат:

- `Отправлено: 0`;
- `пропущено: 1`;
- `ошибок: 0`;
- пользователь без email отсутствует в списке получателей;
- в журнале уведомлений есть запись email со статусом `failed` и причиной «у пользователя не указан email».

Пользователь без email нельзя выбрать в списке получателей: это поведение панели. Пропущенный получатель проверяется по журналу уведомлений, а не по списку.

### SMTP не настроен

1. Временно очистите `SMTP_HOST` в `.env` и перезапустите приложение.
2. Нажмите «Отправить отчёт сейчас» при выбранном получателе.
3. Проверьте сообщение на `/backups` и журнал `/notifications`.

Ожидаемый результат: `ошибок` равно числу выбранных получателей, в журнале есть причина «SMTP не настроен».

## 7. Права

1. Войдите под пользователем с ролью «Продавец».
2. Проверьте верхнее меню: ссылки «Резервные копии» быть не должно.
3. Откройте `/backups` напрямую.

Ожидаемый результат: HTTP 403. Продавец не может запускать копии, менять настройки, скачивать архивы, восстанавливать или отправлять отчёты администратора.

## 8. Ручной `pg_restore` вне `PATH`

1. На тестовой машине разместите рядом `pg_dump.exe` и `pg_restore.exe` в каталоге, который не добавлен в `PATH`.
2. В `/backups` укажите полный путь к `pg_dump.exe` и сохраните.
3. Проверьте, что «Проверка окружения» показывает путь к обоим файлам.
4. На тестовой копии нажмите «Восстановить» у заведомо рабочей копии.

Ожидаемый результат: восстановление использует соседний `pg_restore.exe`, а не ищет его только в `PATH`.

## 9. Импорт из 1С

### Условия

Импорт пишет реальные строки в базу, поэтому выполняйте его на отдельной тестовой базе или на свежей копии рабочей базы, а не на единственной рабочей копии.

Перед началом:

- выполните `alembic upgrade head` — импорту нужна таблица `import_map` (ревизия `5d8c1e4a7b90`), а справочнику единиц — таблица `units` (ревизия `8e2f1a9c4b71`); без них разделы не работают;
- войдите под администратором: права `import.manage` и `units.manage` есть только у суперроли;
- положите выгрузку в папку из поля «Путь» на `/import` (по умолчанию `.system_folder/1c_export/`) и нажмите «Сохранить».

### Эталон

Последняя проверенная реальная выгрузка — 1С 8.3.18 «Розница 2.2», прогон `Export27` от 26.09.2026:

| Что | Сколько |
|---|---|
| Товаров | 5 854 |
| Клиентов | 995 |
| Заказов | 1 344 |
| Позиций заказов | 6 431 |
| Битых `product_id` | 0 |
| Битых `customer_id` | 0 |
| Заказов без контрагента | 17 |

Если ваша выгрузка другая, сначала прогоните на ней разбор и сверьте числа с самой выгрузкой: отличить ошибку импорта от другой выгрузки можно только так. Ноль битых `product_id` в эталоне означает, что в этой выгрузке не создаётся ни одного товара из строк заказов, поэтому счётчик «Товаров создать» здесь совпадает с фактом. В выгрузке с битыми ссылками счётчик занижен: такие товары учитываются отдельно и на странице не показаны.

### 9.1. Разбор ничего не пишет

1. Скопируйте `.system_folder/1c_export/структура_экспорта.json` в папку импорта под другим именем, например `mini.json`.
2. Откройте `/import`, отметьте `mini.json` и нажмите «Разобрать».
3. Запомните количество товаров, клиентов и заказов в базе до и после.
4. Перепишите предупреждения из разбора, если они есть: **это единственное место, где виден их текст.** После импорта страница сообщает только количество, а повторный разбор того же файла даёт ноль предупреждений.

Ожидаемый результат: на странице появился разбор с числами, но в базе ничего не изменилось. Это обязательное поведение: предпросмотр и импорт используют один и тот же код разбора, но предпросмотр не пишет.

### 9.2. Импорт одного файла

1. На `/import` нажмите «Импортировать» с отмеченным `mini.json`.
2. Откройте карточку созданного товара, клиента и заказа.
3. Откройте `/audit`, найдите запись действия `import.run` и посмотрите поле с отчётом — там должны быть те же числа и текст предупреждений, которые были видны в разборе.

Ожидаемый результат:

- создано 1 товар, 1 клиент, 1 заказ;
- артикул товара имеет вид `1C-00001` (в выгрузке артикула нет, а поле обязательное и уникальное);
- цена товара равна 0 и категория не задана, даже если в файле они были; у клиента пустые телефон и email;
- номер заказа взят из нумерации приложения, а не из выгрузки;
- позиция заказа ссылается на товар из базы (в этом файле `product_id` задан и известен), её название и единица взяты из карточки товара, цена — из выгрузки; скидка заказа нулевая, поэтому итог совпадает с суммой позиций;
- остаток товара равен 0, учёт остатков включён — и его нельзя выключить разом, только в карточке товара;
- в базе появилась строка соответствия: `import_map` содержит записи типов `product`, `customer` и `order`, у заказа в `source_label` лежит номер из 1С:

```powershell
$env:PGPASSWORD="smartsklad"; psql -h localhost -U smartsklad -d smartsklad -c "select entity_type, source_id, entity_id, source_label from import_map order by id;"
```

### 9.3. Нулевые остатки блокируют заказы

1. Попробуйте создать заказ на импортированный товар.
2. Введите остаток на карточке товара кнопкой «Сохранить остаток» и повторите создание заказа.

Ожидаемый результат: первая попытка отклоняется с сообщением о нехватке остатка, после ручного ввода остатка заказ создаётся. Это ожидаемое следствие того, что в выгрузке 1С остатков нет, и главный сценарий, о котором нужно предупредить пользователя. Проверьте, что глобальная настройка «учёт остатков по умолчанию» не влияет на уже импортированные товары: чтобы выключить учёт, нужна галочка «Учитывать остатки» в карточке конкретного товара, массового действия нет.

### 9.4. Повторный импорт ничего не создаёт

1. Не меняя файл, нажмите «Разобрать» и посмотрите числа.
2. Нажмите «Импортировать» ещё раз.
3. Сравните количество товаров, клиентов и заказов в базе с предыдущим шагом и выполните `select count(*) from import_map;`.

Ожидаемый результат: разбор показывает 0 создаваемых записей, импорт создаёт 0 записей, количество строк в базе и в `import_map` не изменилось. Повторный прогон безопасен: у найденных по имени товаров и клиентов защита идёт от повторного создания по названию, а у созданных импортом — от строки в `import_map`. Обратите внимание: предупреждений во втором разборе не будет вовсе, поэтому сверяйтесь с записью `import.run` в `/audit`, а не с повторным разбором.

### 9.5. Неизвестные единицы останавливают импорт

Шаг обязателен для настоящей выгрузки и выполняется до 9.6. Раздел рассчитан на **одну** неизвестную единицу — этого достаточно; если в файле их несколько, шаги 4–6 выполняются для каждой. Учесть: `структура_экспорта.json` из репозитория содержит только единицу «шт», а она есть в справочнике, поэтому на файле из пунктов 9.1–9.2 этот шаг не проявится. Чтобы увидеть остановку, используйте настоящую выгрузку или правильную копию файла так, чтобы в нём встретилась хотя бы одна единица, которой нет в справочнике.

1. Запомните содержимое справочника «Единицы измерения» (`/units`) до прогона: названия и количество строк.
2. Откройте `/import`, отметьте файл и нажмите «Разобрать».
3. Убедитесь, что блок «Неизвестные единицы измерения» не пуст, а кнопки «Импортировать» на странице нет. Выпишите названия из блока — по ним потом сверите справочник.
4. Введите в «Название новой» название уже существующей единицы (например, «кг») — вариант «создать новую» в списке слева уже выбран по умолчанию, менять его не нужно — и нажмите «Применить выбор и разобрать заново».
5. Откройте `/units` в соседней вкладке и убедитесь, что новая строка не появилась, — вернитесь на `/import`, очистите «Название новой» полностью и нажмите «Применить выбор и разобрать заново» ещё раз.
6. Верните в «Название новой» подставленное из 1С название (или исправьте его на то, которое хотите) и снова нажмите «Применить выбор и разобрать заново».
7. Нажмите «Разобрать» в блоке файлов, убедитесь, что решения сбросились и блок неизвестных вернулся, затем примените решение заново, как в шаге 6, и убедитесь, что кнопка «Импортировать» появилась.
8. Выполните импорт.
9. Откройте `/units` и сверьте с шагом 1: добавились только те единицы, для которых вы оставили новое название. Молчаливых дублей («ГРАММ» рядом с «г» без вашего решения) быть не должно.
10. Откройте любой импортированный заказ и сравните единицу в позиции с единицей в карточке товара, на который позиция ссылается.

Ожидаемый результат:

- **шаг 3**: пока в разборе есть неизвестные единицы, импорт недоступен, и прямой `POST /import/run` без решений тоже ничего не пишет;
- **шаг 4**: в блоке «Применённые единицы измерения» строка показывает «1С: X → кг», и в справочнике не добавилось ничего. `new:<название>`, совпавшее с существующей единицей, переиспользует её молча: без предупреждения и без записи `unit.create` в аудите. Дубля не будет, но и единицы под новым названием не появится;
- **шаг 5**: страница возвращает «Ошибка: название единицы обязательно» и остаётся на форме решения. Исходная строка 1С не подставляется: пустое поле не даёт завести единицу, и в базе не пишется ничего;
- **шаг 6**: в блоке «Применённые единицы измерения» строка показывает «1С: X → <то название, которое вы ввели>», блока неизвестных единиц больше нет, а кнопка «Импортировать» на месте;
- **шаг 7**: после повторного «Разобрать» решения сбросились и неизвестные единицы предложены снова — решения нигде не хранятся, ни между разборами, ни после них;
- **шаг 9**: отдельного счётчика «создано единиц» в разборе нет, поэтому сверять число нужно по справочнику;
- **шаг 10**: в позиции заказа и в карточке товара одна и та же единица. Переименование единицы проверяется отдельно, в разделе 10.

Отдельно к сведению, вручную не проверяется: единицы, заведённые решением, пишутся в той же транзакции, что и товары с заказами, — при сбое импорта откатываются вместе с ними. На успешном прогоне это видно только косвенно, а ломать импорт ради проверки не нужно.

### 9.6. Полная выгрузка

1. Убедитесь, что в папке лежит настоящая выгрузка, и запустите разбор. Если импорт остановился на неизвестных единицах, пройдите сначала 9.5 — без решений кнопки «Импортировать» не будет.
2. Сверьте числа разбора с эталоном выше: «Товаров создать» — 5 854, «Клиентов создать» — 995, «Заказов создать» — 1 344, «Заказов пропустить» — 0, «ИНН отброшено» — по вашей выгрузке, «Служебный клиент» — «нужен».
3. Выполните импорт и откройте несколько заказов: статус «Выполнен», даты из выгрузки, позиции ссылаются на товары, сумма позиций совпадает с выгрузкой.
4. Откройте клиента «Без контрагента (1С)» и посмотрите его заказы — там должны быть 17 заказов без контрагента.
5. Проверьте, что количество строк выросло на числа разбора, а не в несколько раз: повторного списания остатков не было, все заказы уже «Выполнены». В эталонной выгрузке битых `product_id` нет, поэтому лишних товаров из позиций не появится; в выгрузке с битыми ссылками их будет столько, сколько показывает `orders.products_from_items` в ответе `POST /api/import/preview`.
6. Откройте заказ, попавший на клиента с персональной скидкой, если такой найдётся, и сравните его итог с суммой позиций.

Ожидаемый результат: числа совпадают с эталоном, битых ссылок на товары и клиентов нет (в разборе нет предупреждений об отсутствующем товаре), лишних дублей нет. Итог заказа равен сумме позиций за вычетом персональной скидки клиента, поэтому у клиента со скидкой он законно меньше суммы позиций; у клиентов, созданных импортом, скидка нулевая и итог равен сумме позиций.

### 9.7. Права

1. Войдите под пользователем с ролью «Менеджер».
2. Проверьте верхнее меню: ссылки «Импорт» и «Единицы измерения» быть не должно.
3. Откройте `/import` напрямую, затем запрос `GET /api/import/files` из консоли браузера.
4. Откройте `/units` напрямую, затем выполните в консоли браузера `fetch('/api/units').then(r => console.log(r.status))` и `fetch('/api/units', {method:'POST', headers:{'Content-Type':'application/json'}, body: JSON.stringify({name:'проба'})}).then(r => console.log(r.status))`.

Ожидаемый результат: `/import` и `GET /api/import/files` отвечают HTTP 403; `/units` и `POST /api/units` — тоже, а `POST` не создаёт строку в справочнике. При этом `GET /api/units` отвечает 200 и отдаёт справочник: чтение единиц открыто всем, у кого есть `products.view`, и менеджеру этого права хватает. Импорт и правка единиц недоступны продавцу, кладовщику и менеджеру; выдать `import.manage` и `units.manage` можно только осознанно, через `/roles`.

## 10. Единицы измерения

### Условия

Права `units.manage` нет ни у одной системной роли, поэтому проверяйте под администратором (суперроль). Работайте на тестовой копии базы: удаление единицы необратимо из интерфейса.

### 10.1. Добавление, дубль, переименование

1. Откройте `/units`, посчитайте строки.
2. Введите в «Новая единицу» название, которого нет, и нажмите «Добавить».
3. Введите то же название ещё раз в другом регистре и с пробелами по краям — добавьте.
4. Нажмите «Сохранить» в строке добавленной единицы, не меняя её название.
5. Переименуйте единицу в её строке на новое и нажмите «Сохранить».
6. Откройте `/audit`, найдите записи с типом сущности `unit`.

Ожидаемый результат: шаг 2 добавляет строку, сообщение «Единица добавлена»; шаг 3 отклоняется с «единица с таким названием уже есть» (регистр и пробелы не имеют значения); **шаг 4 тоже отклоняется с тем же текстом** — отправка неизменённого названия считается дублем, потому что проверка находит саму переименовываемую строку; шаг 5 даёт «Единица переименована» и меняет колонку «Изменена» на эту единицу. В аудите видны `unit.create` и `unit.update` типа `unit`, причём у переименования в старом значении лежит прежнее название.

Ограничение длины в 32 символа через страницу не проверить: у поля стоит `maxlength=32`, браузер не даст ввести больше, а обрезанное название пройдёт как обычное. Проверку сервера покрывают автотесты `tests/test_units.py` — `test_create_unit_accepts_name_at_limit_and_rejects_longer` и `test_update_unit_accepts_name_at_limit_and_rejects_longer`: ровно 32 символа принимаются, 33 отклоняются. Вручную её можно проверить запросом `POST /api/units` из консоли браузера: 33 символа дают HTTP 422 с текстом «название длиннее 32 символов».

### 10.2. Удаление занятой единицы

1. Создайте товар с единицой из шага 10.1.
2. Удалите этот товар через «Удалить» на карточке, не восстанавливая.
3. Попробуйте удалить единицу в справочнике.
4. Уберите товар из работы окончательно: восстановите его и переведите на другую единицу, затем попробуйте удалить единицу снова.

Ожидаемый результат: шаг 3 отклоняется с «единица используется товарами» — **удалённый товар тоже мешает**, потому что он не стирается из базы. Единица удаляется только тогда, когда на неё не ссылается ни один товар, включая удалённые. Проверьте, что в базе строка осталась, а пропала из списка:

```powershell
$env:PGPASSWORD="smartsklad"; psql -h localhost -U smartsklad -d smartsklad -c "select id, name, is_deleted from units order by id;"
```

### 10.3. Переименование не трогает историю заказов

1. Возьмите единицу, которая стоит у товара, попавшего в выполненный заказ.
2. Переименуйте её в справочнике.
3. Откройте карточку этого товара и выполненный заказ, обновите обе страницы.
4. Откройте печатную форму заказа (`/orders/{id}/print`).

Ожидаемый результат: в карточке товара, в списке товаров и в печатной форме единицы может быть по-разному: карточка показывает новое название, а позиция заказа — старое, потому что в позиции хранится снимок названия на момент продажи. Расхождение ожидаемо, это не ошибка. Убедитесь, что карточка товара не потребовала никакой правки, а в аудите появилась одна запись `unit.update` на единицу, а не по записи на каждый товар.

### 10.4. Три состояния `unit_id` в API товара

Проверяется из консоли браузера под пользователем с правами `products.edit` и `price.change` (суперроль подходит). `<id>` — номер товара из его адреса на `/products/<id>`, единицу товара смотрите в блоке «Единица измерения» на карточке.

1. Создайте товар с единицей, отличной от «шт» (например, «кг»), и запомните его номер.
2. Частичный PATCH без `unit_id` — поменяйте только цену:

```javascript
fetch('/api/products/' + id, {method:'PATCH', headers:{'Content-Type':'application/json'}, body: JSON.stringify({price: 123})}).then(r => r.json()).then(d => console.log(d.unit, d.unit_id))
```

3. PATCH с явным `null`:

```javascript
fetch('/api/products/' + id, {method:'PATCH', headers:{'Content-Type':'application/json'}, body: JSON.stringify({unit_id: null})}).then(r => r.json()).then(d => console.log(d.unit, d.unit_id))
```

4. PATCH с несуществующим `unit_id`:

```javascript
fetch('/api/products/' + id, {method:'PATCH', headers:{'Content-Type':'application/json'}, body: JSON.stringify({unit_id: 999999})}).then(r => console.log(r.status))
```

5. POST без `unit_id` — новый товар:

```javascript
fetch('/api/products', {method:'POST', headers:{'Content-Type':'application/json'}, body: JSON.stringify({name:'Проба', sku:'PROBA-' + Date.now(), price: 10})}).then(r => r.json()).then(d => console.log(d.unit, d.unit_id))
```

Ожидаемый результат: состояний именно три, а не два. Шаг 2 — цена поменялась, а единица осталась прежней: в консоли должно вывести «кг», потому что `unit_id` в запросе не было. Шаг 3 — единица стала «шт»: явный `null` это сброс, а не «не менять». Шаг 4 — HTTP 409 «единица не найдена», единица товара при этом не изменилась. Шаг 5 — новый товар с единицей «шт». Это различие между шагами 2 и 3 главное: отправка `null` в частичном PATCH тихо переводит товар в штучные, а отсутствие поля — нет.
