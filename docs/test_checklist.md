# Чек-лист ручной проверки

Пункты 1–8 проверяют резервное копирование, восстановление и отчёт по email. Раздел 9 проверяет импорт из 1С.

## Общие условия

Проверки выполняются на отдельной тестовой базе или на копии рабочей базы. Не выполняйте восстановление на единственной рабочей копии.

Перед началом:

- запустите приложение из корня проекта;
- войдите под пользователем с правом `backup.manage`;
- откройте `/backups`;
- убедитесь, что в «Проверке окружения» найдены `pg_dump` и `pg_restore`, а папка доступна для записи;
- сохраните идентификатор тестовой базы и не используйте рабочие SMTP-данные без необходимости.

## 1. Ручная копия

1. Нажмите «Создать копию сейчас».
2. Дождитесь сообщения «Копия создана».
3. Обновите `/backups`.
4. Проверьте, что новый файл появился в таблице «Резервные копии».
5. В «Последних запусках» проверьте запись вида `manual` со статусом `success` и именем файла.

Ожидаемый результат: файл имеет имя вида `smartsklad-YYYYMMDD-HHMMSS.dump`, временного `.part` в списке нет.

## 2. Срок хранения

1. В настройках установите срок хранения `1` день и сохраните.
2. В тестовой папке создайте файл с корректным именем, например `smartsklad-20260101-000000.dump`. Это подготовка тестового архива: в интерфейсе отдельного поля для ручного имени нет.
3. Нажмите «Создать копию сейчас».
4. Проверьте список архивов.

Ожидаемый результат: после успешной копии старый файл исчез, а свежая копия осталась. Проверка выполняется только после успешного создания новой копии.

## 3. Отсутствие `pg_dump`

1. В настройках укажите заведомо неверный полный путь к `pg_dump` и сохраните.
2. Обновите `/backups` и проверьте блок «Проверка окружения».
3. Дождитесь планового запуска на тестовой базе. Для проверки можно установить время запуска в прошлом, включить автоматическое копирование и убедиться, что копии за текущий день ещё не было.
4. Проверьте «Последние запуски».
5. Откройте обычную страницу приложения, например `/products`.

Ожидаемый результат: в панели есть красное предупреждение о ненайденном `pg_dump`; в последних запусках есть ошибка планового запуска; приложение продолжает открываться и не падает.

После проверки верните корректный путь или очистите поле, чтобы копирование снова работало.

## 4. Восстановление на тестовой копии

**Обязательно выполнять только на тестовой копии базы.**

1. Создайте клиента и товар, если они ещё не нужны для сценария.
2. Создайте первый заказ и сохраните его номер.
3. Нажмите «Создать копию сейчас» и дождитесь успешного файла.
4. Создайте второй заказ с другим понятным номером или признаком.
5. Убедитесь, что второй заказ виден в `/orders`.
6. На странице `/backups` нажмите «Восстановить» у копии из шага 3. Форма использует задержку 60 секунд; во время обратного отсчёта не редактируйте данные. В баннере проверьте абсолютное время начала и при необходимости нажмите «Отменить восстановление».
7. После начала восстановления откройте обычную страницу приложения, например `/orders`. Кнопка отмены во время работы `pg_restore` не должна останавливать процесс.

Ожидаемый результат:

- во время работы `pg_restore` обычная страница отвечает HTTP 503;
- после завершения приложение снова открывается;
- второй заказ исчез;
- первый заказ остался;
- состояние сессий соответствует снятой копии: сессии, созданные до копии, остаются, а созданные после копии исчезают;

Если первый заказ тоже отсутствует либо появились неожиданные данные, остановитесь и не повторяйте восстановление на рабочей базе.

## 5. Advisory-lock и два процесса

Этот сценарий проверяется вручную на PostgreSQL, потому что тесты используют SQLite.

1. Подготовьте тестовую базу и одинаковый `.env` для двух процессов.
2. В `/backups` включите автоматическое копирование, установите период проверки `1` минуту и время запуска в прошлом. Убедитесь, что за текущий день автоматическая копия ещё не создавалась.
3. Запустите два отдельных процесса приложения из двух окон PowerShell одинаковой командой:

```powershell
uvicorn "app.main:app" --port 8001
```

и:

```powershell
uvicorn "app.main:app" --port 8002
```

Не используйте эти два процесса для рабочего режима восстановления: состояние технического обслуживания хранится в памяти процесса.

4. Дождитесь плановой проверки.
5. Сравните количество новых архивов и записей `scheduled` в «Последних запусках».

Ожидаемый результат: за один плановый момент создана одна копия, а не по одной копии на каждый процесс. Второй процесс должен получить advisory-lock и пропустить выполнение задания.

## 6. Отчёт по email

### Успешная ручная отправка

1. Настройте тестовый SMTP в `.env`, перезапустите приложение и создайте активного пользователя с корректным email.
2. В `/backups` откройте «Отчёт по email».
3. Выберите пользователя, настройте частоту и период данных, время, нажмите «Сохранить».
4. Нажмите «Отправить отчёт сейчас».

Ожидаемый результат: приходит одно письмо с отчётом и CSV-вложением. В панели появляется сообщение с количеством отправленных, пропущенных и ошибочных попыток. Расписание и список получателей не меняются; ручной запуск обновляет `last_report_at`, `last_report_sent` и `last_report_skipped`, а следующий плановый запуск всё ещё определяется по `last_report_scheduled_at`. Количество ошибок видно в сообщении, но не сохраняется; причины по получателям находятся в `notification_log`.

### Пропуск пользователя без email

1. Создайте пользователя с email, сохраните его в получателях и нажмите «Сохранить».
2. Удалите email у этого пользователя через карточку пользователя.
3. Не нажимайте «Сохранить» в настройках отчёта, чтобы сохранённый id остался в настройках.
4. Нажмите «Отправить отчёт сейчас».
5. Проверьте `/notifications` и счётчик «пропущено» в `/backups`.

Ожидаемый результат:

- `Отправлено: 0`;
- `пропущено: 1`;
- `ошибок: 0`;
- пользователь без email отсутствует в списке получателей;
- в журнале уведомлений есть запись email со статусом `failed` и причиной «у пользователя не указан email».

Пользователь без email нельзя выбрать в списке получателей: это поведение панели. Пропущенный получатель проверяется по журналу уведомлений, а не по списку.

### SMTP не настроен

1. Временно очистите `SMTP_HOST` в `.env` и перезапустите приложение.
2. Нажмите «Отправить отчёт сейчас» при выбранном получателе.
3. Проверьте сообщение на `/backups` и журнал `/notifications`.

Ожидаемый результат: `ошибок` равно числу выбранных получателей, в журнале есть причина «SMTP не настроен».

## 7. Права

1. Войдите под пользователем с ролью «Продавец».
2. Проверьте верхнее меню: ссылки «Резервные копии» быть не должно.
3. Откройте `/backups` напрямую.

Ожидаемый результат: HTTP 403. Продавец не может запускать копии, менять настройки, скачивать архивы, восстанавливать или отправлять отчёты администратора.

## 8. Ручной `pg_restore` вне `PATH`

1. На тестовой машине разместите рядом `pg_dump.exe` и `pg_restore.exe` в каталоге, который не добавлен в `PATH`.
2. В `/backups` укажите полный путь к `pg_dump.exe` и сохраните.
3. Проверьте, что «Проверка окружения» показывает путь к обоим файлам.
4. На тестовой копии нажмите «Восстановить» у заведомо рабочей копии.

Ожидаемый результат: восстановление использует соседний `pg_restore.exe`, а не ищет его только в `PATH`.

## 9. Импорт из 1С

### Условия

Импорт пишет реальные строки в базу, поэтому выполняйте его на отдельной тестовой базе или на свежей копии рабочей базы, а не на единственной рабочей копии.

Перед началом:

- выполните `alembic upgrade head` — импорту нужна таблица `import_map` (ревизия `5d8c1e4a7b90`), без неё раздел не работает;
- войдите под администратором: право `import.manage` есть только у суперроли;
- положите выгрузку в папку из поля «Путь» на `/import` (по умолчанию `.system_folder/1c_export/`) и нажмите «Сохранить».

### Эталон

Последняя проверенная реальная выгрузка — 1С 8.3.18 «Розница 2.2», прогон `Export27` от 26.09.2026:

| Что | Сколько |
|---|---|
| Товаров | 5 854 |
| Клиентов | 995 |
| Заказов | 1 344 |
| Позиций заказов | 6 431 |
| Битых `product_id` | 0 |
| Битых `customer_id` | 0 |
| Заказов без контрагента | 17 |

Если ваша выгрузка другая, сначала прогоните на ней разбор и сверьте числа с самой выгрузкой: отличить ошибку импорта от другой выгрузки можно только так.

### 9.1. Разбор ничего не пишет

1. Скопируйте `.system_folder/1c_export/структура_экспорта.json` в папку импорта под другим именем, например `mini.json`.
2. Откройте `/import`, отметьте `mini.json` и нажмите «Разобрать».
3. Запомните количество товаров, клиентов и заказов в базе до и после.

Ожидаемый результат: на странице появился разбор с числами, но в базе ничего не изменилось. Это обязательное поведение: предпросмотр и импорт используют один и тот же код разбора, но предпросмотр не пишет.

### 9.2. Импорт одного файла

1. На `/import` нажмите «Импортировать» с отмеченным `mini.json`.
2. Откройте карточку созданного товара, клиента и заказа.

Ожидаемый результат:

- создано 1 товар, 1 клиент, 1 заказ;
- артикул товара имеет вид `1C-00001` (в выгрузке артикула нет, а поле обязательное и уникальное);
- номер заказа взят из нумерации приложения, а не из выгрузки;
- позиция заказа ссылается на товар из базы, её название и единица взяты из карточки товара, цена — из выгрузки;
- остаток товара равен 0, учёт остатков включён;
- в базе появилась строка соответствия: `import_map` содержит записи типов `product`, `customer` и `order`, у заказа в `source_label` лежит номер из 1С:

```powershell
$env:PGPASSWORD="smartsklad"; psql -h localhost -U smartsklad -d smartsklad -c "select entity_type, source_id, entity_id, source_label from import_map order by id;"
```

### 9.3. Нулевые остатки блокируют заказы

1. Попробуйте создать заказ на импортированный товар.
2. Введите остаток на карточке товара кнопкой «Сохранить остаток» и повторите создание заказа.

Ожидаемый результат: первая попытка отклоняется с сообщением о нехватке остатка, после ручного ввода остатка заказ создаётся. Это ожидаемое следствие того, что в выгрузке 1С остатков нет, и главный сценарий, о котором нужно предупредить пользователя. Массового ввода остатков в этой версии нет.

### 9.4. Повторный импорт ничего не создаёт

1. Не меняя файл, нажмите «Разобрать» и посмотрите числа.
2. Нажмите «Импортировать» ещё раз.
3. Сравните количество товаров, клиентов и заказов в базе с предыдущим шагом и выполните `select count(*) from import_map;`.

Ожидаемый результат: разбор показывает 0 создаваемых записей, импорт создаёт 0 записей, количество строк в базе и в `import_map` не изменилось. Приложение помнит, во что стала каждая запись выгрузки, поэтому повторный прогон безопасен.

### 9.5. Полная выгрузка

1. Убедитесь, что в папке лежит настоящая выгрузка, и запустите разбор.
2. Сверьте числа разбора с эталоном выше: «Товаров создать» — 5 854, «Клиентов создать» — 995, «Заказов создать» — 1 344, «Заказов пропустить» — 0, «ИНН отброшено» — по вашей выгрузке, «Служебный клиент» — «нужен».
3. Выполните импорт и откройте несколько заказов: статус «Выполнен», даты из выгрузки, позиции ссылаются на товары, итог заказа совпадает с выгрузкой.
4. Откройте клиента «Без контрагента (1С)» и посмотрите его заказы — там должны быть 17 заказов без контрагента.
5. Проверьте, что количество строк в базе выросло на числа разбора, а не в несколько раз: повторного списания остатков не было, все заказы уже «Выполнены».

Ожидаемый результат: числа совпадают с эталоном, битых ссылок на товары и клиентов нет (в разборе нет предупреждений об отсутствующем товаре), лишних дублей нет.

### 9.6. Права

1. Войдите под пользователем с ролью «Менеджер».
2. Проверьте верхнее меню: ссылки «Импорт» быть не должно.
3. Откройте `/import` напрямую, затем `GET /api/import/files`.

Ожидаемый результат: страница `/import` и запрос `GET /api/import/files` отвечают HTTP 403. Импорт недоступен продавцу, кладовщику и менеджеру; выдать `import.manage` можно только осознанно, через `/roles`.
