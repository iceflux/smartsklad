- 2026-09-20: модели внутри модулей — изоляция границ.
- 2026-09-20: тесты на SQLite in-memory, dev на PostgreSQL — `pytest` одной командой без Docker.
- 2026-09-20: Tailwind через CDN в Спринт 1 — заменить на оффлайн-сборку при деплое.
- 2026-09-20: сессии в БД на cookie (не JWT) — task.md §5, проще отозвать/инвалидировать.
- 2026-09-20: bcrypt напрямую (не passlib) — passlib заброшен, bcrypt хватает.
- 2026-09-20: password recovery — токен по email, тихий отказ при неизвестном аккаунте — не раскрываем существование аккаунтов.
- 2026-09-20: seed админа из .env при пустой БД — в Спринте 2 нет UI CRUD пользователей.
- 2026-09-21: роли с наборами прав вместо фиксированного enum + создание кастомных ролей — по запросу владельца (была ограничена MVP, решение задокументировано).
- 2026-09-21: роль admin — суперроль (is_super): все права всегда, чек-боксы для неё неактивны — исключает блокировку админа при правке прав.
- 2026-09-21: упрощённая модель inventory по запросу владельца — характеристики одним JSON-полем `characteristic` вместо таблицы `product_attributes`; поля товара сведены к name/sku/unit/price/rest (без full_name/vat_rate/weight/image_url/min_stock).
- 2026-09-21: права на PATCH товара — по-полям (rest→stock_change, price→price_change, остальное→products_edit, несколько полей = AND) — нельзя обойти products_edit чрез price_change.
- 2026-09-21: Спринт 3 реализован as-designed: роли/права, inventory, UI audit-логов.
- 2026-09-21: карточка клиента с полем `comment` — запрос владельца.
- 2026-09-21: удаление клиентов — мягкое (`is_deleted`), как у товаров; жёсткое удаление сломает историю заказов FK в Спринте 5.
- 2026-09-21: право на клиентов — одно `customers.manage` (view+edit), по task.md §14; статистика клиента — Спринт 5.
- 2026-09-22: Спринт 5 реализован as-designed: модуль orders — снимки позиций, статусы со списанием/возвратом остатков, мягкое удаление, история изменений в UI, статистика клиента.
- 2026-09-22: скидки только в процентах 0..99 (строки и заказ), дефолт заказа — `customer.personal_discount` — по брифу, без денежных сумм.
- 2026-09-22: снимки позиций в `OrderItem` (имя/цена/скидка/единица) — заказ не меняется при последующих правках товара/цены/скидки клиента.
- 2026-09-22: номер заказа по `max(id)+1` без unique-constraint — не concurrency-safe, известно для MVP; при росте нагрузки — unique + retry.
- 2026-09-22: глобальная настройка учёта остатков (`stock_track_default`) + per-product override (`Product.track_rest`) — общий режим по умолчанию с возможностью исключения по товару.
- 2026-09-22: `track_rest` фиксируется при создании товара, глобальная настройка не влияет задним числом на существующие товары — предсказуемое поведение остатков.
- 2026-09-22: `track_rest=False` — полное отключение учёта в заказах (проверка остатка, списание при done, возврат) — товар вне складского контура; проверка `qty>=1` остаётся.
- 2026-09-22: существующие товары при внедрении `track_rest` → `True` (server_default true) — не менять поведение уже заведённых позиций.
- 2026-09-23: гибрид печати — HTML-предпросмотр (Jinja2 `autoescape=True`, `@media print`) + PDF через ReportLab; WeasyPrint исключён (тяжёлая WebKit-зависимость, ReportLab хватает для MVP).
- 2026-09-23: фиксированный шаблон печати `documents/order_print.html` — редактор макетов позже, по запросу.
- 2026-09-23: ручная отправка документов без вложений (email/telegram — только текст заказа) — PDF-вложение в Спринте 6.1.
- 2026-09-23: Telegram на единый `chat_id` из настроек — без персональных чатов для MVP.
- 2026-09-23: настройки Telegram (`telegram_bot_token`/`telegram_chat_id`) в таблице settings с маскировкой токена в UI — секрет не показывается целиком.
- 2026-09-23: права `notifications.send`/`notifications.view` у admin+manager (seller/warehouseman нет) — уведомления и журнал — зона менеджеров.
- 2026-09-23: email уведомлений отправляется на `customer.email` — единственный известный адрес клиента.
- 2026-09-25: PDF-вложение при отправке заказа включается всегда, оба канала (email и telegram), настройка не предусмотрена; текст в telegram идёт как caption документа.
- 2026-09-25: пользователи только деактивируются (`is_active`), удаления нет — жёсткое удаление сломало бы ссылки на автора аудита и заказов.
- 2026-09-25: ошибки сервиса пользователей — подклассы `ValueError` (`UserConflictError` → 409, `UserPermissionError` → 403), валидация → 422 — сервис остаётся HTTP-agnostic, статус выбирает роутер.
- 2026-09-25: `update_user` сначала валидирует все переданные поля и только потом применяет их — ошибка в одном поле не оставляет частично изменённого пользователя в сессии.
- 2026-09-25: не-супер с `users.manage` не может менять супер-пользователей (включая пароль) и не может выдать супер-роль — иначе `users.manage` давал бы эскалацию до admin.
- 2026-09-25: пароль нового пользователя генерируется на сервере при каждом открытии `/users/new` (`secrets.choice` по `user_password_charset`/`user_password_length`) и может быть отредактирован до отправки; открытая страница пароль не сохраняет.
- 2026-09-25: на форме создания пароль показывается открытым текстом, в форме редактирования — маскируется — значение и так лежит в атрибуте `value`, маскировка ничего не защищает; копирование кнопкой отпадает, `navigator.clipboard` работает только в secure context (HTTPS/localhost), а склад раздаётся по HTTP в локальной сети.
- 2026-09-25: проверка «последнего активного супера» блокирует строки через `SELECT … FOR UPDATE` и считает в Python, а не `COUNT` — `FOR UPDATE` нельзя применять к агрегатам, поэтому блокировка доступна только при выборке id; под READ COMMITTED вторая транзакция после ожидания перечитывает строки и видит уже деактивированного супера.
- 2026-09-25: прогноз спроса считается линейной регрессией на stdlib, а не scikit-learn — отклонение от task.md §6: на товар приходятся десятки точек, RandomForest бессмысленен, а sklearn тянет numpy+scipy+joblib (~250 МБ) под проект, спроектированный под слабое железо.
- 2026-09-25: формула закупки исправлена на `прогноз + min_stock > остаток` — в task.md §6 было `прогноз − остаток < min_stock`, что предлагало закупать при избытке.
- 2026-09-25: продажи датируются `Order.created_at`, отдельная отметка времени перехода в `done` не добавлена — колонка `completed_at` стоила бы миграции без ретроспективного заполнения; погрешность на границах дней принята как ограничение MVP.
- 2026-09-25: день продажи определяется датой в часовом поясе сессии БД; окно берётся от `date.today()` часов хоста. Для текущей развёртки (локальный PostgreSQL и приложение на одной машине) это один и тот же пояс — проверено: `SHOW timezone` возвращает `Europe/Moscow`, локальное время БД совпадает с часами хоста. При переносе БД на другую машину или в другой пояс это допущение перестанет выполняться, и дневные корзины могут сместиться.
- 2026-09-25: `min_stock` по умолчанию выводится из глобальной настройки «запас в днях», переопределение задаётся в штуках на карточке товара.
- 2026-09-25: фолбэк на скользящее среднее при прогнозе не используется — порог в 14 дней с продажами гарантирует достаточность данных для регрессии, фолбэк был бы мёртвым кодом.
- 2026-09-25: периоды аналитики — скользящие окна 1/7/30/365 дней, а не календарные: календарный период в начале месяца даёт пустую аналитику; в UI подписи показывают фактический диапазон.
- 2026-09-25: график продаж рисуется инлайновым SVG, а не Chart.js — ноль новых зависимостей, а читаемость длинных периодов обеспечивается адаптивным `viewBox`, а не переключением на недельные/месячные корзины.
- 2026-09-25: индексы на `orders.created_at` и `orders.status` не добавляются — агрегаты идут последовательным сканом, что приемлемо на объёме MVP; добавим при росте таблицы, как уже решено для `max(id)+1` в номерах заказов.
- 2026-09-25: отправка отчёта на email и расписание рассылки вынесены из спринта аналитики — планировщик строится вместе с бэкапами (task.md §8 п.10), чтобы не реализовывать его дважды.
- 2026-09-25: день продажи определяется датой в часовом поясе сессии БД — то же допущение, что зафиксировано для прогноза спроса.
- 2026-09-25: бэкап снимается `pg_dump` без остановки приложения — утилита делает согласованный дамп при параллельной работе, поэтому режим обслуживания нужен только для восстановления.
- 2026-09-25: копия пишется во временный файл и переименовывается после успешного завершения — прерванный дамп не должен выглядеть как рабочая копия.
- 2026-09-25: `pg_restore --clean --if-exists` работает в существующей базе, а не с `--create` — пересоздание самой базы под работающим приложением опаснее пересоздания объектов.
- 2026-09-25: пароль БД передаётся утилитам только через `PGPASSWORD`, никогда в `argv` и логи.
- 2026-09-25: состояние режима обслуживания живёт в памяти процесса, поэтому приложение обязано работать одним процессом; дубликаты фоновых задач закрываются advisory-lock.
- 2026-09-25: отчёт по email отправляется отдельным письмом каждому получателю — один некорректный адрес не должен ронять общую SMTP-транзакцию.
- 2026-09-25: получатели отчёта — выбранные пользователи, а не свободный список адресов: адрес живёт в карточке пользователя и меняется вместе с ним; пользователи без email не попадают в UI-список, а пропуски видны в журнале уведомлений.
- 2026-09-25: проверка версии `pg_dump` против версии сервера показывается в панели заранее — утилита отказывается снимать сервер новее себя.
